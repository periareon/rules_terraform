rules_terraform

Overview

This repository implements Bazel rules for Terraform and OpenTofu.

Setup

Add rules_terraform to your MODULE.bazel:

bazel_dep(name = "rules_terraform", version = "{version}")

Toolchains for both engines are auto-registered — no use_extension or register_toolchains call is required. By default a build uses the newest release shipped in //terraform/private:versions.bzl / //tofu/private:versions.bzl; those tables carry the three newest releases of each engine.

Any other release is one tag away. The extension fetches that release's SHA256SUMS once and records the checksums as facts in MODULE.bazel.lock, so pinning an older engine needs no change to rules_terraform:

terraform = use_extension("@rules_terraform//terraform:extensions.bzl", "terraform")
terraform.toolchain(version = "1.9.8", default = True)   # default = True: use it unless the flag says otherwise

tofu = use_extension("@rules_terraform//tofu:extensions.bzl", "tofu")
tofu.toolchain(version = "1.9.1")                        # available, selected by flag

The flags select among the releases the hub knows, shipped or tagged:

--@rules_terraform//terraform/settings:version=1.9.8
--@rules_terraform//tofu/settings:version=1.9.1

Left empty they mean "the default": the root module's default = True tag, else the newest shipped release.

Nothing has to be installed on the host: the engine binary, provider archives and registry modules are all fetched by Bazel, and every bazel run / bazel test below uses the toolchain-fetched engine.

Getting started

A root module that is new to Bazel usually has .tf files and nothing else. The provider lock file is the one artifact the rules need and the source tree may not have yet, so the first steps produce it.

  1. Declare the module. A terraform_module is one directory of .tf files. No lock, no deps yet:

    load("@rules_terraform//terraform:defs.bzl", "terraform_module", "terraform_providers_lock")

terraform_module(
    name = "app",
    srcs = glob(["*.tf"]),
)

# Writes .terraform.lock.hcl next to this BUILD file, for every platform
# in the default set, using the toolchain's terraform. Needs network.
terraform_providers_lock(
    name = "providers_lock.update",
    output = ".terraform.lock.hcl",
    target = ":app",
)

  2. Generate the lock and commit it:

    bazel run //path/to/app:providers_lock.update

    Rerun it whenever a required_providers block changes. There is no step that runs terraform from your PATH.

  3. Declare the module's dependencies in MODULE.bazel, one deps tag per lock file:

    terraform = use_extension("@rules_terraform//terraform:extensions.bzl", "terraform")
terraform.deps(
    name = "app_deps",
    lock = "//path/to/app:.terraform.lock.hcl",
    roots = ["//path/to/app:main.tf"],   # only if main.tf names registry modules
)
use_repo(terraform, "app_deps")

  4. Wire the module up and add the workflow targets:

    load("@rules_terraform//terraform:defs.bzl", "terraform_binary", "terraform_providers_lock_test", "terraform_validate_test")

terraform_module(
    name = "app",
    srcs = glob(["*.tf"]),
    deps = ["@app_deps"],   # the providers, the lock, and the registry modules
)

terraform_binary(name = "terraform", root = ":app")       # bazel run //path/to/app:terraform -- plan
terraform_validate_test(name = "validate", target = ":app")
terraform_providers_lock_test(                            # fails when the lock drifts from the sources
    name = "providers_lock",
    lock = ".terraform.lock.hcl",
    target = ":app",
)

  5. Add what the module calls. A local child module is its own terraform_module listed in deps; a registry module comes through the directory being in a deps tag's roots, which the hub above already covers. Both are described under External dependencies and lock files.

A repo with several root modules repeats steps 1 to 4 per root, or shares one lock file across roots as the monorepo example does. Add .terraform/ to .gitignore; the rules never write it into the source tree, but a stray native init would.

To fetch providers and registry modules, declare a deps tag on the terraform extension (or tofu, for OpenTofu): the lock file for providers, the directories with module blocks for registry modules.

terraform = use_extension("@rules_terraform//terraform:extensions.bzl", "terraform")
terraform.deps(
    name = "app",
    lock = "//path/to:.terraform.lock.hcl",   # providers the lock pins
    roots = ["//path/to:main.tf"],             # registry modules named here
)
use_repo(terraform, "app")

Running the engine CLI directly (@terraform / @tofu)

rules_terraform ships two hub repositories — @terraform and @tofu — that let a user invoke the toolchain-resolved engine binary from any subdirectory of their workspace:

cd path/to/my/tf/module
bazel run @terraform -- plan             # ≈ terraform plan
bazel run @terraform -- init             # ≈ terraform init
bazel run @tofu -- state list        # ≈ tofu state list

The wrapper chdirs to $BUILD_WORKING_DIRECTORY (the shell cwd where bazel run was invoked) before exec-ing the engine, so relative paths and any terraform.tfstate land in the directory you're standing in — just like the native CLI. Version resolution follows the same //terraform/settings:version / //tofu/settings:version flags as the rest of the ruleset, so you get one hermetic Terraform release across all invocations.

It is also how a Terraform maintainer manages dependencies without touching Bazel: bazel run @terraform -- init -upgrade or bazel run @terraform -- providers lock in a module directory writes the lock the rules consume, and a module that depends on its providers hub as a whole (deps = ["@my_deps"]) picks the change up with no BUILD edit.

To reformat sources, bazel run @rules_terraform//terraform:format (or //tofu:format) rewrites the .tf files of every module in the workspace with the toolchain engine's fmt; pass target patterns to narrow it. Modules tagged no_format or no_terraform_format are skipped, matching the fmt aspect.

This is NOT the Bazel-managed workflow. @terraform does no init aspect, no lock-file rewriting, no .terraform construction — terraform init still runs against your source tree, hits the network, and writes state. Reach for it when you want a one-off CLI invocation (state manipulation, ad-hoc plan against an unrelated module) without wiring up a terraform_binary target for the module.

To use @terraform / @tofu from downstream, add them to your MODULE.bazel:

terraform = use_extension("@rules_terraform//terraform:extensions.bzl", "terraform")
use_repo(terraform, "terraform")

tofu = use_extension("@rules_terraform//tofu:extensions.bzl", "tofu")
use_repo(tofu, "tofu")

The extensions are already invoked by rules_terraform's own MODULE.bazel, which registers the toolchain hubs; the use_repo line only binds the repo name in your namespace so @terraform / @tofu resolve.

Bazel-managed Terraform

When a terraform_module is built through Bazel, an init aspect assembles the whole module directory hermetically — the directory the engine will run in, .tf files and .terraform/ alike — rather than letting terraform init build it. The result is a single Bazel tree artifact that terraform_binary and the validate rules copy and cd into. Every network fetch happens at repository-rule / bzlmod-extension time; build actions are offline. As a consequence:

  • Provider binaries are fetched at repository-rule time and copied into .terraform/providers/… during the aspect's action. The lock file's h1: hashes are rewritten to match the actually-installed binary layout.
  • External modules (from a Terraform registry) are resolved via a Bazel-owned lock file, downloaded at repository-rule time, and copied into .terraform/modules/… with a generated modules.json manifest.
  • Local child modules — other terraform_module targets in the monorepo — are placed at the relative source path the parent's module block names, so Terraform resolves them the way it resolves any local module. Packages nested under the parent land there automatically; anything else is matched to the module block whose source names it.

A terraform_module is exactly one directory: every file in srcs must live directly in the target's own package, and srcs accepts only what the engine loads: .tf and .tf.json for terraform_module, plus .tofu and .tofu.json for tofu_module. Any other file is an analysis error rather than a file the engine would silently skip. Nested .tf files are a child module and belong in their own terraform_module. This is enforced at analysis time, and it is what lets the aspect know which directory it is building without guessing.

The full mechanics — how the extensions resolve each dependency type, what each lock file looks like, and how to keep them fresh — are in External dependencies and lock files below.

Direct terraform CLI incompatibility

Once a terraform_module has Bazel-managed dependencies, running terraform (or tofu) directly outside Bazel is not expected to work: the module directory is Bazel's construction, h1: hashes are rewritten for the installed platform binary, and modules.json reflects the Bazel target graph — not the source tree.

Use bazel run to invoke the engine:

# Instead of: terraform plan
bazel run //path/to:terraform -- plan

# Instead of: terraform apply
bazel run //path/to:terraform -- apply

The terraform_binary rule creates an executable that copies the aspect-built module directory into a writable temp dir and runs the real terraform binary there.

That temp dir is removed when the command finishes. A module with a backend or cloud block is unaffected: its state belongs to the backend. A module with neither keeps its state where the native CLI keeps it, the working directory, which here is the temp dir, so by default the state goes with the run: disposable_state on the terraform_module is True. A run that did write state is kept and its path printed, so the record of what an apply created never vanishes silently, but the next run starts from a fresh copy and does not see it. Any state sitting in the module's source directory is ignored.

Where the state has to outlive the run and there is still no backend (bootstrapping the bucket that will hold real state, a sandbox applied and destroyed over days), set disposable_state = False. The runner then points the engine's local backend at terraform.tfstate (and terraform.tfstate.d/ for workspaces) in a per-module directory under bazel-out/rules_terraform/, and names it after every state-writing command. That directory is private to the machine and bazel clean deletes it, state included; nothing is written to the source tree. Setting it on a module that declares a backend is an error. Relative file arguments (-out=tfplan, -var-file=x.tfvars) resolve against the temp dir, so pass absolute paths.

Because the aspect already installed the providers and the module manifest, the only thing a run-time terraform init still contributes is backend setup — so it runs only for subcommands that need one. version, fmt, validate, test and metadata skip it and work offline against a module with a remote backend; plan, apply and the rest initialize the backend as before. The practical consequences: a terraform_test on a module with a remote backend needs no credentials, and a configuration error in one of those subcommands is reported as itself rather than as a backend failure.

Workspaces. The rules add no workspace concept of their own; they use Terraform's. TF_WORKSPACE in the environment selects one for every project in a run, so --action_env=TF_WORKSPACE=prod validates every module in prod under the aspect and --test_env=TF_WORKSPACE=prod does the same for the test rules. A root whose configuration is keyed on terraform.workspace gets each of its workspaces checked by one test target per workspace, with the workspace attribute of terraform_validate_test, terraform_test or terraform_plan_test forcing it, and no_validate on the module where the default workspace is not a valid one. bazel run reads TF_WORKSPACE the same way. A workspace select inside a bazel run changes only the staged copy, which is gone when the command finishes, so it does not carry to the next run and the runner says so; workspace new still creates the workspace in the backend. Every run picks its workspace up front, from the environment, and nothing a previous run selected leaks into it.

terraform_validate_test, the validate aspect and terraform_test run the engine with the operator's CLI configuration disabled (TF_CLI_CONFIG_FILE pointed at an empty file, CHECKPOINT_DISABLE=1, TF_IN_AUTOMATION=1), so a ~/.terraformrc on one machine cannot change what a check reports. bazel run keeps the full environment, since that is where credential helpers live.

Tests and review artefacts

terraform_test runs the engine's native test framework. Each run block is reported as a JUnit test case through XML_OUTPUT_FILE, so bazel test summaries and CI dashboards show which run failed rather than one opaque target. Terraform writes the report itself with -junit-xml; for OpenTofu, which has no such flag, the runner builds it from the -json-into event stream and keeps that stream too. The lock file and module manifest the test ran against land in the undeclared outputs directory (bazel-testlogs/<pkg>/<name>/test.outputs/).

terraform_plan_test runs a real plan and keeps plan.tfplan, plan.json and plan.txt as undeclared outputs, so a plan can be reviewed from CI artefacts. It passes when the plan succeeds, or with expect_no_changes only when the plan is empty. A plan reaches the backend and the provider APIs, so the macro tags the target requires-network; credentials go through --test_env. Providers that work offline (null, local, random) need neither. Plans and state hold sensitive values, so treat those artefacts as you would the state itself.

For validation and formatting, use the corresponding test rules:

terraform_validate_test(
    name = "validate_test",
    target = ":my_module",
)

terraform_fmt_test(
    name = "fmt_test",
    target = ":my_module",
)

External dependencies and lock files

rules_terraform partitions external Terraform state into three buckets, each with its own resolution path and (where applicable) lock file. Every network fetch happens at repository-rule / bzlmod-extension time — build actions never touch the network. What Terraform actually sees at run time is a fully-populated module directory.

At a glance

The deps tag

Both halves of a root module's external dependencies are declared on one tag, because that is how the engine treats them: terraform init installs the providers the lock pins and the registry modules the module blocks name in one step. The hub it produces, @<name>, is a terraform_dependency_group carrying both, and a terraform_module that depends on it needs no lock attribute.

terraform = use_extension("@rules_terraform//terraform:extensions.bzl", "terraform")
terraform.deps(
    name = "my_deps",
    lock = "//path/to:.terraform.lock.hcl",       # optional: providers
    roots = ["//path/to:main.tf"],                 # optional: registry modules
    # registry = "registry.opentofu.org",          # default follows the extension
)
use_repo(terraform, "my_deps")

Either half may be omitted: a shared library that names a registry module but no provider gets a tag with roots only. The parts are addressable too: @my_deps//:providers, @my_deps//:modules, and @my_deps//<namespace>_<name> for one provider.

Providers

The lock file is Terraform's native .terraform.lock.hcl. Write it with the terraform_providers_lock updater (see Getting started); it runs the toolchain engine, so no terraform install is involved.

At repo-rule time the extension:

  1. Reads the lock file via module_ctx.read.

  2. For every (provider, platform) pair, calls https://<registry>/v1/providers/<namespace>/<name>/<version>/download/<os>/<arch> via module_ctx.download(...) and reads the returned JSON to obtain the archive download_url + shasum. The shasum must be one of the lock entry's zh: hashes — those are the archive checksums recorded when the lock was written — so the registry can tell Bazel where the archive is but not what it should contain.

    A platform is left out of the hub only when the registry's own /v1/providers/<namespace>/<name>/versions listing says the version was never published for it. Every other way a lookup can come up empty (the registry is unreachable, the lock names a version or host the registry does not know) fails the evaluation with the URL that was tried. Nothing is ever recorded about a lookup that failed, so a transient outage cannot leave a platform permanently missing from MODULE.bazel.lock. A provider published for none of the requested platforms is likewise an error, not a silently thinner hub.

    Answers are cached in module_ctx.facts: one entry per archive, plus the published-platform list for a provider that is missing a default platform. With MODULE.bazel.lock enabled a re-evaluation makes no provider requests at all.

  3. Declares an http_archive per distinct archive, in a pool shared by every providers hub. The repository is named from the archive's identity (rt_prov_<registry>_<namespace>_<name>_<version>_<platform>), so two lock files that agree on a provider version fetch and extract it once. Archives are lazy — Bazel only fetches the platform your build actually resolves.

  4. Emits the hub: @my_deps carries every provider in the lock plus the lock itself, and @my_deps//<namespace>_<name> is a per-provider alias that picks the right pool archive via select(). Depend on @my_deps and the module needs no lock attribute: a Terraform maintainer who adds a provider edits required_providers and regenerates the lock, and no BUILD file changes. Depend on individual aliases plus lock to install a subset.

At build time terraform_init_aspect extracts each provider's files into .terraform/providers/<registry>/<namespace>/<name>/<version>/<platform>/ and recomputes the h1: hash in a copy of the lock file it writes inside .terraform/. That rewrite is what lets terraform init -get=false accept the Bazel-installed binaries.

Regenerating. Wire up a terraform_providers_lock target (or tofu_providers_lock for the OpenTofu variant):

load(
    "@rules_terraform//terraform:terraform_providers_lock.bzl",
    "terraform_providers_lock",
)

terraform_providers_lock(
    name = "providers_lock",
    output = ".terraform.lock.hcl",
    target = ":my_module",
    # Optional; defaults to a 5-platform set (linux/darwin ×
    # amd64/arm64 + windows_amd64).
    # platforms = ["linux_amd64", "darwin_arm64"],
)

bazel run //:providers_lock seeds a temp directory with your .tf sources, runs terraform providers lock -platform=<all> under the toolchain-fetched engine binary, and writes the multi-platform result back into $BUILD_WORKSPACE_DIRECTORY. This is the only path that produces hashes for every platform at once — the engine's own init locks the platform it runs on only.

Drift check. terraform_providers_lock_test fails if the lock file does not match what the module tree requires. It reads the directory the init aspect built, every module in it including installed registry and git modules, and counts both the providers a required_providers { … } block declares and the ones resource, data, ephemeral and provider blocks imply, the way the engine does. No network, no engine. The lock's own hashes are enforced elsewhere: the extension refuses an archive whose checksum is not among the lock's zh: entries, and the engine verifies each installed provider directory against the h1: the init aspect wrote.

Providers built in the repo

A provider that is not on any registry — one you build from source in the same workspace — is a terraform_provider whose files is the built binary. It is used exactly like a hub-provided provider:

load("@rules_go//go:def.bzl", "go_binary")
load("@rules_terraform//terraform:defs.bzl", "terraform_module", "terraform_provider")

go_binary(
    name = "terraform-provider-custom",   # the engine requires this prefix
    srcs = ["main.go"],
)

terraform_provider(
    name = "custom",
    files = [":terraform-provider-custom"],
    source = "example/custom",             # matches `required_providers`
    version = "1.0.0",
)

terraform_module(
    name = "app",
    srcs = glob(["*.tf"]),
    lock = ".terraform.lock.hcl",
    deps = [":custom"],
)

Leave platform unset: it is read from the configuration the provider is built in, so the same target works on a Linux CI runner and an Apple Silicon laptop. The .terraform.lock.hcl still needs an entry for the provider — write one by hand with the version and a placeholder h1: hash; the init aspect replaces the h1: with the hash of the binary it actually installed. A module that depends on providers but has no lock is an analysis error, since the engine will not use a provider directory it cannot check against one.

External registry modules

Terraform has no lock file for modules, so the extension keeps its own record: each module block's constraint is resolved against the Registry API once, and the version it chose is written as a fact to MODULE.bazel.lock. Every later evaluation declares that version until an upgrade is asked for. Terraform users load the extension from the terraform side:

terraform.deps(
    name = "shared",
    lock = "//:.terraform.lock.hcl",
    # Every directory whose `module` blocks name a registry module, root
    # modules and shared libraries alike, given as any .tf file inside it.
    roots = [
        "//envs/prod/app:main.tf",
        "//modules/naming:main.tf",
    ],
)

Then every terraform_module whose blocks name a registry module depends on @shared (or @shared//:modules for a library that should not install providers). Archives are pooled, and a module depending on the hub depends on a candidate pool from which only what its own module blocks name is installed, so a tag may list many directories. The monorepo example does this across three environments and a shared library.

OpenTofu users load the parallel extension — same tag class, but the registry defaults to registry.opentofu.org:

tofu = use_extension("@rules_terraform//tofu:extensions.bzl", "tofu")
tofu.deps(
    name = "app",
    lock = "//:.terraform.lock.hcl",
    roots = ["//:main.tf"],
)
use_repo(tofu, "app")

At extension eval time the impl reads every *.tf file in each directory listed in roots (matching Terraform's own "root module is a directory" model), parses module { source = "…" } blocks, and for every registry-shaped source:

  1. Hits /v1/modules/<ns>/<name>/<provider>/versions and picks the highest version satisfying the block's version constraint via a Starlark port of Terraform's semver logic.
  2. Hits /v1/modules/<ns>/<name>/<provider>/<version> for metadata — reads source (git URL) and tag, constructs a direct GitHub tarball URL (<source>/archive/refs/tags/<tag>.tar.gz) with the matching strip_prefix.
  3. Downloads the archive to compute the sha256.
  4. Once every modules tag has been resolved, registers one http_archive per distinct (registry, module address, version) in a pool shared by every hub (rt_mod_<registry>_<address>_<version>), extracted whole. Each //subdir any hub referenced is a target inside that one repository rather than a second download. The hub itself is a terraform_module_group over the pool targets it resolved to.

Every downstream fetch goes direct to GitHub — no registry hop at build time. Only GitHub-backed modules are supported; non-GitHub git hosts fail with a clear error at eval time. A source written with its own hostname (app.terraform.io/acme/vpc/aws) is resolved against that host rather than the tag's registry.

Git modules

A module block whose source is a git address is resolved by the same roots scan, with no registry involved:

module "vpc" {
  source = "git::ssh://git@git.example.com/acme/terraform-modules.git//vpc?ref=v1.4.0"
}

The three spellings Terraform accepts are all recognised: a forced git::https://… or git::ssh://… address, the scp-like git@host:org/repo.git, and the github.com/org/repo shorthand. Each may carry //subdir and ?ref=. A version on a git block is an error, as it is for Terraform; the ref is the pin.

The ref must be a tag or a full commit id. A branch moves, so nothing built from one is reproducible: a branch name, or a source with no ?ref= at all, is an error at evaluation time. A commit id is exact by construction. A tag is looked up once and what it names is recorded in MODULE.bazel.lock, so every later evaluation declares the same thing even if the tag is moved afterwards.

GitHub over https needs no git at all. The extension fetches the archive GitHub serves for the ref (archive/refs/tags/<tag>.tar.gz or archive/<commit>.tar.gz), exactly as it does for a registry module: unpacked once on a facts miss to record its integrity and read the module's own external references, then declared as an http_archive pinned by that integrity, named rt_git_<host_path>_<ref>. The tag form of the URL is not found for a branch, which is how a branch is refused on this path. A moved tag fails the next fresh fetch on integrity rather than being followed. The github.com/org/repo shorthand takes this path.

Every other remote, ssh:// to GitHub included, goes through the host's git. On a facts miss the extension asks the remote whether the ref is a tag (ls-remote --tags), refuses it if not, checks the tag or commit out one commit deep, records the commit and the module's own references, and discards the checkout. The repository Bazel builds against is a new_git_repository of that exact commit, named rt_git_<host_path>_<commit> and shared by every spelling and every hub that reaches it. It is fetched with the host's git and its credentials, so a private remote works wherever git clone of it would. git has to be on PATH both when the extension evaluates and when the repository is fetched.

Either way, references found inside a git module are followed like a registry module's: a git module that names a registry module, or another git module, brings it into the hub. For a ref the facts already hold nothing is fetched.

Not handled: ?sshkey= (credentials come from the host's git configuration or, for GitHub archives, Bazel's downloader through .netrc or a credential helper), submodules, and non-git remote sources such as plain https:// archives or s3::. Those are supplied by hand, below.

Modules the extension cannot fetch — a registry module hosted off GitHub, or a plain https:// / s3:: source — can still be supplied by hand. Fetch the archive with whatever repository rule fits, declare a terraform_external_module in its build file with source copied verbatim from the module block, and put the target in deps:

# MODULE.bazel
http_archive = use_repo_rule("@bazel_tools//tools/build_defs/repo:http.bzl", "http_archive")
http_archive(
    name = "acme_vpc",
    urls = ["https://git.example.com/acme/terraform-vpc/-/archive/v1.4.0/terraform-vpc-v1.4.0.tar.gz"],
    strip_prefix = "terraform-vpc-v1.4.0",
    integrity = "sha256-…",
    build_file_content = """
load("@rules_terraform//terraform:defs.bzl", "terraform_external_module")
terraform_external_module(
    name = "module",
    # Verbatim from the `module` block. No `version`: that is for registry modules.
    source = "https://git.example.com/acme/terraform-vpc/-/archive/v1.4.0/terraform-vpc-v1.4.0.tar.gz",
    srcs = glob(["**/*.tf"]),
    visibility = ["//visibility:public"],
)
""",
)

The init aspect installs it under every module block whose source matches, the same way it places a registry module.

At build time the init aspect copies each module's files into .terraform/modules/<key>/ and adds a corresponding entry to Terraform's modules.json manifest.

Reproducibility and caching. The extension is reproducible = True: every answer it ever took from the network, a constraint's resolved version, a tag's commit, an archive's URL and integrity, is a fact in MODULE.bazel.lock, so the same inputs and facts declare the same repositories. Every .tf edit in a root directory still re-evaluates it (bzlmod tracks each module_ctx.read()), but a re-evaluation with warm facts makes no network calls. Facts persist only while the lockfile is enabled. To re-resolve on purpose, set RULES_TERRAFORM_UPGRADE=1 in the environment of one bazel fetch (or pass --repo_env=RULES_TERRAFORM_UPGRADE=1); the extension sees the variable through module_ctx.getenv, so setting and clearing it each count as an input change. See Reproducibility and the Implementation detail: network calls per eval note below.

Non-default registries. Pass registry = "…" on the tag if you're pointing at a private mirror or an alternate registry; it applies to the providers and the modules of that tag alike.

Implementation detail: network calls per eval

For each module { } block, the extension issues up to three Registry API requests, cached across evals via module_ctx.facts:

CallPurposeCostSkipped when
GET /v1/modules/<source>/versionsResolve version constraint to a concrete SemVerSmall JSONversion is an exact pin, or facts hold resolve:<registry>/<source>@<constraint> and no upgrade was asked for
GET /v1/modules/<source>/<version>Read source (git URL) + tag to build the archive URLSmall JSONFacts cache has an entry for <source>@<version>
GET <archive URL>Stream the archive body to compute an sha256 integrityMB per moduleFacts cache has an entry for <source>@<version>

Two kinds of fact are kept. <source>@<concrete_version> stores {url, strip_prefix, integrity} and the module's own external references: historical facts that don't change once a version is published. resolve:<registry>/<source>@<constraint> stores the version a constraint resolved to, which is a choice rather than a property, and is only revisited under RULES_TERRAFORM_UPGRADE. Only entries for currently-declared modules carry across evals; entries for removed modules prune naturally.

Local / in-repo modules

Modules living inside your monorepo don't need a lock file — Bazel's own target graph is the source of truth.

Give the child its own terraform_module and list it in the parent's deps. The path lives in one place — the module block — and deps just says which target supplies it, the way a py_library dep supplies an import:

# root/main.tf
module "greeter" {
  source = "./modules/greeter"
}

terraform_module(
    name = "root",
    srcs = glob(["*.tf"]),
    deps = ["//root/modules/greeter"],
)

When the child's package sits under the parent's — the usual case, //root/modules/greeter beneath //root — the aspect places it at modules/greeter inside the module directory, which is already what source = "./modules/greeter" names.

When it doesn't, the source path is matched against the tail of each dep's package. A child at //shared/greeter satisfies source = "./greeter"; nothing changes in the BUILD file:

terraform_module(
    name = "root",
    srcs = glob(["*.tf"]),
    deps = ["//shared/greeter"],
)

Two mistakes are build errors rather than a silently wrong module directory: a local source no dep supplies, and a terraform_module dep no module block references. If two deps could satisfy the same source, that's an error too — rename one directory or nest it under the parent's package.

Reproducibility

Every bzlmod extension in rules_terraform is reproducible = True: given the same tags, the same files, and the same facts, it declares the same repositories.

PartWhere its answers come from
toolchain tagURL and integrity vendored in //<engine>/private:versions.bzl; a tagged release's checksums fetched once and kept as facts.
deps tag, lock halfThe checked-in .terraform.lock.hcl pins versions and hashes; the registry is asked only where each archive lives, and that answer is a fact.
deps tag, roots halfA version constraint or git ref is resolved once; the version or commit it named is a fact, and so are the archive's URL and integrity.

The role of MODULE.bazel.lock

Facts live in the lockfile. That is what turns "resolved once" into "resolved once per repository" rather than once per machine:

  1. Reproducibility. ~> 5.0 resolves to 5.7.1 today and would resolve to 5.7.2 tomorrow. The first evaluation records 5.7.1 as a fact; every evaluation after that, on any machine, declares 5.7.1 until someone asks for an upgrade. The choice is in the lockfile, in the diff, and in review.

  2. Performance. Every .tf edit under a roots directory re-evaluates the extension (bzlmod tracks each module_ctx.read()). With warm facts a re-evaluation makes no network calls; without the lockfile there are no facts, and every re-evaluation resolves and downloads from scratch.

Recommended downstream setup — in your consuming repo's .bazelrc:

common --lockfile_mode=update
# or, once you're confident in the state:
common --lockfile_mode=strict

Commit MODULE.bazel.lock. This gives you deterministic module versions regardless of how loosely the .tf constraints are written, cheap re-evaluations, and a PR-visible diff whenever a resolution changes.

--lockfile_mode=off is the one way to opt out: with nothing to hold facts, every evaluation resolves live, exactly as terraform init does.

Exact pins are still worth writing. A block pinned to 5.7.1 skips even the first /versions call, and it is the only form the native terraform init also treats as fixed, so it is what keeps the Bazel and non-Bazel workflows on the same module code.

Upgrading

A recorded resolution is kept on purpose, so a newer release of a module does not arrive by itself. To take it:

  1. Run RULES_TERRAFORM_UPGRADE=1 bazel fetch //... (or --repo_env=RULES_TERRAFORM_UPGRADE=1). Every version constraint and git ref is resolved again and the facts are rewritten. Facts that are properties of a published version, an archive's integrity, are kept.
  2. Review the MODULE.bazel.lock diff and commit it with any .tf change.

Editing a module block's source or version is itself a new key, so a changed block resolves on the next bazel fetch without the switch.

rules_terraform's own MODULE.bazel.lock

The ruleset commits its lockfile. Its own test fixtures use the extension, so the lockfile is what keeps bazel test //... here offline and repeatable, and a PR that bumps a fixture's module version shows the resolved archive in the diff. The examples under examples/ run with --lockfile_mode=off on purpose: they stand in for a downstream user's first build, where no facts exist yet.

Terraform Extensions

One module extension lives in //terraform:extensions.bzl, terraform, with two tag classes.

terraform.toolchain

The extension always materializes one hub repo (@terraform_toolchains) that declares a toolchain per (version, platform) for the releases shipped in //terraform/private:versions.bzl — the three newest when the table was generated — and @terraform, the CLI hub. rules_terraform's own MODULE.bazel use_repos the toolchain hub and register_toolchainss it, so downstream users get toolchain resolution for free. Per-(version, platform) http_archives are lazy; only the selected combination is fetched.

A toolchain tag adds any other release. The extension fetches that release's SHA256SUMS once and records the checksums as facts in MODULE.bazel.lock.

# Nothing to do beyond `bazel_dep` to use the newest shipped release.
bazel_dep(name = "rules_terraform", version = "...")

# To use another release:
terraform = use_extension("@rules_terraform//terraform:extensions.bzl", "terraform")
terraform.toolchain(version = "1.9.8", default = True)

versionstring (required)The release, e.g. 1.9.8. Shipped releases need no tag.

terraform.deps

The deps tag class: the providers a lock file pins and the registry and git modules some directories' module blocks name, as one hub per tag.

terraform = use_extension("@rules_terraform//terraform:extensions.bzl", "terraform")

# One `deps` tag per lock file. `lock` brings the providers the lock pins;
# `roots` brings the registry and git modules named by the `module` blocks
# in those directories (root modules and shared libraries alike). Either may
# be omitted.
terraform.deps(
    name = "app",
    lock = "//path/to/module:.terraform.lock.hcl",
    roots = [
        "//path/to/module:main.tf",
        "//path/to/library:main.tf",
    ],
    # registry = "registry.opentofu.org",  # optional; defaults to registry.terraform.io
)

use_repo(terraform, "app")

@app is a terraform_dependency_group: every provider in the lock, the lock itself, and every external module the roots name. A terraform_module that depends on it needs no lock attribute. @app//:providers and @app//:modules are the two halves, and @app//<namespace>_<name> is one provider. Name the hub after what it serves rather than after the tag.

Hubs are alias layers. The archives themselves go into pools shared by every hub of the extension: one repository per distinct provider archive (rt_prov_<registry>_<namespace>_<name>_<version>_<platform>) and one per distinct module archive (rt_mod_<registry>_<address>_<version>), so two hubs that agree on a version fetch and extract it once. Hub names share one namespace across every Bazel module that uses the extension; a duplicate is reported at evaluation time.

OpenTofu Extensions

One module extension lives in //tofu:extensions.bzl, tofu, with the same two tag classes as the terraform extension.

tofu.toolchain

The extension always materializes @tofu_toolchains, a hub declaring a toolchain for every OpenTofu release shipped in //tofu/private:versions.bzl and any a toolchain tag requests, each guarded by a config_setting on //tofu/settings:version that the hub itself declares, and @tofu, the CLI hub. rules_terraform's own MODULE.bazel registers the hub so downstream users get toolchain resolution for free.

# Nothing to do beyond `bazel_dep` to use the newest shipped release.
bazel_dep(name = "rules_terraform", version = "...")

# To use another release:
tofu = use_extension("@rules_terraform//tofu:extensions.bzl", "tofu")
tofu.toolchain(version = "1.9.1", default = True)

tofu.toolchain takes the same version and default attributes as the Terraform extension's tag; see the Terraform page. For a tagged release the extension fetches that release's SHA256SUMS once and records the checksums as facts in MODULE.bazel.lock.

tofu.deps

The same deps tag class as the terraform extension, defaulting to registry.opentofu.org. An OpenTofu-only repository uses it for everything and never loads //terraform:extensions.bzl:

tofu = use_extension("@rules_terraform//tofu:extensions.bzl", "tofu")
tofu.deps(
    name = "app",
    lock = "//path/to/module:.terraform.lock.hcl",   # written by tofu
    roots = ["//path/to/module:main.tf"],
)
use_repo(tofu, "app")

The attributes are those documented for the terraform extension; only the default registry differs. That default matters: registry.opentofu.org serves OpenTofu's own builds of the hashicorp/* providers, whose archive hashes differ from HashiCorp's, so a lock file written by tofu has to be resolved against it. Write the lock with the module's tofu_providers_lock updater and it will be.

Each extension pools its own archives. A repository using both engines against the same dependencies should declare them through one extension rather than both, or the same archive is fetched twice.

Public build settings for //tofu.

Each exported function is named after a build setting in this package and its docstring describes what the setting does. The function body returns the setting's label so callers can reference it programmatically.

version

Picks which OpenTofu release the auto-registered toolchains resolve to.

The tofu extension declares one toolchain per (version, platform) for the releases shipped in //tofu/private:versions.bzl — the newest three when the table was generated — and for any release a tofu.toolchain(version = "…") tag asks for. For a tagged release the extension fetches the release's SHA256SUMS once and records the checksums as facts in MODULE.bazel.lock, so an older pin costs no change to rules_terraform and no network on later evaluations.

Empty, the default, selects the extension's default: the release the root module marked toolchain(…, default = True), else the newest shipped one. Any other value names one of the known releases. Set it globally in .bazelrc, per invocation via --@rules_terraform//tofu/settings:version=1.9.1, or per target with a Starlark configuration transition. The corresponding archive is fetched lazily on first use.

Gazelle

rules_terraform ships a Gazelle language per engine. It writes the BUILD files the rules need from the configuration itself: one module target per directory of .tf files, with deps kept in step with the module blocks, and the binary and lock targets for a root.

Setup

# BUILD.bazel at the repository root
load("@gazelle//:def.bzl", "gazelle", "gazelle_binary")

gazelle_binary(
    name = "gazelle_bin",
    languages = [
        "@rules_terraform//terraform/gazelle",
        # "@rules_terraform//tofu/gazelle",  # for OpenTofu directories
    ],
)

gazelle(
    name = "gazelle",
    gazelle = ":gazelle_bin",
)

bazel run //:gazelle then writes or updates BUILD files; bazel run //:gazelle -- -mode diff shows what it would change, which is what a CI check runs.

What a directory becomes

The directoryGenerated
has configuration filesterraform_module(name = <directory name>, srcs = [...], data = [...], deps = [...])
also declares a backend or cloud blockplus terraform_binary(name = "terraform") and terraform_providers_lock(name = "providers_lock.update")
also has a .terraform.lock.hclplus terraform_providers_lock_test(name = "providers_lock"), and the updater if the directory is not a root
holds .tofu filesthe tofu_* kinds instead

srcs are the files the engine loads, .tf and .tf.json, plus .tofu and .tofu.json under OpenTofu. data is everything else a native run in that directory could read: the remaining files, and the contents of subdirectories that are not packages of their own. Build files, the lock, state, and dotfiles are left out, as is anything under .terraform/.

deps has two parts. Every module block with a local source (./… or ../…) resolves to the module target in that directory; a directory nothing generates a target for is reported. Then the dependency hubs: the ones a tf_deps_hub directive names, or, for a root with a lock file and no directive, @tf_<path> with / and - replaced by _.

Rules are merged, not overwritten: a hand-written tags, visibility, or disposable_state stays, comments stay, and an attribute written as a glob() is left alone with a warning, since a list cannot be merged into it. Delete the glob to let Gazelle write the list.

Directives

DirectiveMeaning
# gazelle:tf_engine terraform|tofuWhich engine's rules a directory tree gets. Unset, a directory with .tofu files is OpenTofu's, the rest Terraform's.
# gazelle:tf_kind root|module|autoForce a root (binary and lock targets) or a library. auto, the default, reads the configuration for a backend.
# gazelle:tf_deps_hub NAME...The hubs (@NAME) modules under the directory depend on. An empty value clears an inherited one.
# gazelle:tf_default_visibility LABEL...Visibility written on new library modules under the directory. An existing rule keeps its own.

Directives inherit down the tree, so one tf_deps_hub on a module library's parent directory covers every module in it, and one tf_engine tofu at the repository root makes an OpenTofu-only repository.

What it does not do

It does not write .terraform.lock.hcl; that is providers_lock.update. It does not declare the deps tags in MODULE.bazel; the hub names it writes are the names those tags must have. And it does not read expressions: a module block whose source is not a literal is not resolved.
