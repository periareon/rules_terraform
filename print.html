rules_terraform

Overview

This repository implements Bazel rules for Terraform.

Setup

To begin using the rules, add the following to your MODULE.bazel file.

bazel_dep(name = "rules_terraform", version = "{version}")

terraform = use_extension("@rules_terraform//terraform:extensions.bzl", "terraform")
terraform.toolchain(
    name = "terraform_toolchains",
)
use_repo(terraform, "terraform_toolchains")

register_toolchains(
    "@terraform_toolchains//:all",
)

Bazel-Managed Terraform

When Terraform modules are managed through Bazel, the .terraform directory is assembled hermetically by an init aspect rather than by terraform init. This has several important implications:

  • Provider binaries are fetched at repository-rule time (during bazel fetch / analysis) and copied into the .terraform/providers/ directory structure during the build action. The lock file's h1: hashes are rewritten to match the actual installed binaries.

  • External modules (from the Terraform Registry) are resolved via a lock file (terraform_modules.lock.json) and downloaded at repository-rule time. Their files are placed into .terraform/modules/ with a generated modules.json manifest.

  • Cross-package modules (other terraform_module targets in the monorepo) are wired via the module_sources attribute, which maps Terraform source paths to Bazel target labels. Their files are copied into .terraform/modules/ at build time.

Direct terraform CLI Incompatibility

Once a terraform_module has Bazel-managed dependencies, running terraform commands directly (outside of Bazel) is not expected to work. This is because:

  1. The .terraform directory is assembled by Bazel's init tooling, not terraform init
  2. Lock file h1: hashes are rewritten to match the platform-specific binary that Bazel installed
  3. modules.json is generated by the init tool to reflect Bazel's dependency graph
  4. Provider binaries are copied from Bazel's external repository cache, not downloaded by Terraform

Instead, use bazel run to invoke Terraform:

# Instead of: terraform plan
bazel run //path/to:terraform -- plan

# Instead of: terraform apply
bazel run //path/to:terraform -- apply

The terraform_binary rule creates an executable that sets up a hermetic working directory with all dependencies wired into place before delegating to the real terraform binary.

For validation and formatting, use the corresponding test rules:

terraform_validate_test(
    name = "validate_test",
    target = ":my_module",
)

terraform_fmt_test(
    name = "fmt_test",
    target = ":my_module",
)

terraform_binary

load("@rules_terraform//terraform:defs.bzl", "terraform_binary")

terraform_binary(name, lock, root)

Creates an executable wrapper for running Terraform commands on a specific module.

The .terraform directory is assembled hermetically by the terraform_init_aspect applied to the root module. Providers and modules are resolved from Bazel-managed dependencies rather than from the network.

Important: Once a terraform_module has Bazel-managed dependencies (providers via terraform.providers(), modules via Bazel targets or module_sources), direct terraform CLI usage outside of Bazel is not expected to work. Use bazel run //:my_terraform -- apply instead of invoking terraform directly. The .terraform directory, lock file hashes, and modules.json are all constructed by Bazel's init tooling and may differ from what terraform init would produce.
